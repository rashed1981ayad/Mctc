# منصة منتجات شركة المتقدم

هذا المشروع يضيف للموقع جهتين واضحتين:

- واجهة العميل: يعرض المنتجات، البحث، التصفية، وتفاصيل كل منتج.
- سلة طلب عرض سعر: مشتركة بين العربية والإنجليزية والفرنسية، تحفظ المنتجات والكميات في المتصفح وتُسجل الطلب في PostgreSQL قبل فتح WhatsApp.
- بطاقات المنتجات تحتفظ بزر «+» للإضافة السريعة. في صفحة تفاصيل المنتج تظهر قائمة كمية من 1–30، وتحتها زر الإضافة إلى السلة وبجواره تنزيل الداتا شيت الأساسي إذا كان متاحًا.
- لوحة التحكم: تطبيق React منفصل لإدارة المنتجات والرسائل وطلبات عروض الأسعار. قوائم الإدارة مقسّمة إلى صفحات من 20 سجلًا، مع بحث وفلاتر للمنتجات، وبحث جزئي في الرسائل والطلبات.
- API: مبني بـ Node.js و Express.
- قاعدة البيانات: PostgreSQL باستخدام استعلامات SQL عبر مكتبة `pg`.
- الواجهة: React + Vite.

## هيكل المشروع

```text
client/src/main.jsx              نقطة تشغيل React فقط
client/src/app/                  إعداد التطبيق والمسارات
client/src/components/           المكونات المشتركة مثل Header و Footer وبطاقة المنتج
client/src/pages/                صفحات العميل فقط
admin/src/                       تطبيق لوحة التحكم المستقل
admin/dist/                      ملفات اللوحة المبنية، يقدمها الخادم بعد التحقق من الجلسة
server/public/admin-login.html   صفحة الدخول الصغيرة المتاحة دون جلسة
client/src/hooks/                Hooks صفحات العميل
client/src/services/             الاتصال بالـ API ومساعدات المنتجات
client/src/constants/            الأقسام والعلامات التجارية والثوابت
client/src/styles/               ملفات CSS مقسمة حسب أجزاء الواجهة
server/                          API، جلسات المدير، وحماية ملفات اللوحة
server/sql/                      ملف SQL مرجعي لإنشاء الجداول
assets/                          أصول الموقع
```

الواجهة تستخدم الآن `react-router-dom` للتنقل و `@tanstack/react-query` لإدارة طلبات الخادم والتخزين المؤقت.

## التشغيل المحلي باستخدام PostgreSQL

1. ثبّت PostgreSQL على جهازك وشغّله.

2. افتح أداة PostgreSQL مثل `psql` أو `pgAdmin`، ثم أنشئ قاعدة بيانات باسم:

```sql
create database almutqaddim;
```

3. انسخ ملف الإعدادات:

```bash
cp server/.env.example server/.env
```

4. عدّل `server/.env` حسب بيانات PostgreSQL عندك.

مثال:

```env
DATABASE_URL=postgres://postgres:your_password@localhost:5432/almutqaddim
```

غيّر `your_password` إلى كلمة مرور PostgreSQL الخاصة بك.

5. ثبّت الحزم:

```bash
npm install
npm --prefix client install
npm --prefix admin install
npm --prefix server install
```

6. شغّل المشروع:

```bash
npm run dev
```

أمر التطوير يضبط `NODE_ENV=development` لخادم API تلقائيًا؛ بعد تحديث هذا الإعداد أوقف العملية القديمة وأعد تشغيل `npm run dev` حتى تظهر أداة Turnstile التجريبية في لوحة التحكم.

قبل التشغيل الأول، جهّز الجداول وحساب المدير باستخدام `npm --prefix server run db:prepare` مع اتصال إداري مستقل في `MIGRATION_DATABASE_URL`. ثم اضبط `DATABASE_URL` لحساب التشغيل المحدود كما هو موضح أدناه. لا ينشئ خادم الويب الجداول أو يرقّيها في التطوير أو الإنتاج، ولا يعيد المنتجات التجريبية بعد حذفها. لإضافة المنتجات التجريبية يدويًا في بيئة اختبار فقط استخدم `npm --prefix server run db:seed`.

## الروابط

- واجهة العميل أثناء التطوير: `http://127.0.0.1:5173/`
- لوحة التحكم أثناء التطوير: `http://127.0.0.1:5174/login` (خادم Vite مستقل؛ يمرر `/login` و`/api` و`/uploads` إلى Express على المنفذ 5000).
- يجب إبقاء `npm run dev` قيد التشغيل. المنفذان 5173 و5174 ثابتان؛ إذا كان أحدهما مشغولًا يظهر خطأ بدل الانتقال إلى منفذ مختلف.
- في الإنتاج: `https://admin.mctc.ly/login`، وبعد الدخول تنتقل إلى `/products`، ولا يمكن تنزيل ملفات اللوحة دون جلسة.
- API: `http://127.0.0.1:5000/api`
- فحص السيرفر: `http://127.0.0.1:5000/api/health`
- استعراض بيانات PostgreSQL بعد تسجيل دخول المدير: `http://127.0.0.1:5174/api/database` (كما يعيد رابط `/api` توجيه المدير إليه). تعرض الاستجابة جداول المنتجات والرسائل والطلبات وعناصرها والمديرين، مع استبعاد كلمات المرور ورموز الجلسات.
- سجل تدقيق الإدارة: `http://127.0.0.1:5174/api/database/admin_audit_events`، محمي بجلسة المدير ومقسّم إلى صفحات. في الإنتاج استخدم `https://admin.mctc.ly/api/database/admin_audit_events`.

لفتح البيانات في المتصفح في الإنتاج: سجّل الدخول أولًا من `https://admin.mctc.ly/login`، ثم افتح `https://admin.mctc.ly/api`. استخدم روابط `url` داخل الاستجابة لعرض جدول منفرد؛ كل جدول يعرض 20 سجلًا في الصفحة، ويمكن استخدام `?page=2&limit=100` للتنقل (بحد أقصى 100 سجل في الطلب).
- السلة: `/cart` أو `/en/cart` أو `/fr/cart` حسب اللغة.

## إعدادات المدير والأمان

ضع بريد المدير وكلمة مرور قوية وفريدة في `server/.env` قبل التشغيل الأول. يُنشئ الخادم الحساب عند أول تشغيل، ولا يغيّر كلمة مرور حساب موجود عند تعديل الملف لاحقًا؛ إذا سبق استخدام بيانات تجريبية، غيّر كلمة مرور الحساب في قاعدة البيانات قبل النشر. لا ترفع ملف `.env` إلى مستودع عام.

لتغيير كلمة مرور حساب موجود من Git Bash دون كتابتها ضمن سجل الأوامر:

```bash
read -r -s -p "كلمة المرور الجديدة: " NEW_ADMIN_PASSWORD
echo
export NEW_ADMIN_PASSWORD
npm --prefix server run admin:password
unset NEW_ADMIN_PASSWORD
```

يجب أن تكون الكلمة الجديدة 16 حرفًا على الأقل. يبطل الأمر جلسات المدير السابقة. بعد تغييرها يمكن حذف `ADMIN_PASSWORD` القديمة من `server/.env`؛ فهي مطلوبة فقط لإنشاء حساب جديد لأول مرة. يرفض الخادم التشغيل بـ`NODE_ENV=production` إذا بقيت كلمة المرور التجريبية القديمة فعّالة.

عند استخدام حساب قاعدة بيانات محدود في الإنتاج، يتطلب أمر تغيير كلمة المرور `MIGRATION_DATABASE_URL` بصلاحيات إدارية في بيئة تنفيذ الأمر فقط؛ لا تحفظه في ملف `.env` الخاص بخادم الويب، وأزله من بيئة الطرفية بعد انتهاء الأمر.

تُحفظ الجلسات في جدول `admin_sessions` داخل PostgreSQL. المتصفح يحمل Cookie من نوع `HttpOnly` بدل تخزين رمز الدخول في `localStorage`، وطلبات التعديل تستخدم رمز CSRF. تسجيل الخروج يبطل الجلسة على الخادم. يجب تشغيل الإنتاج عبر HTTPS مع `NODE_ENV=production` حتى يُضبط خيار `Secure` للـCookie.

يسجّل جدول `admin_audit_events` محاولات الدخول الناجحة والفاشلة والمحدودة، وتسجيل الخروج، وعمليات إضافة المنتجات وتعديلها وحذفها، وتغيير حالات الطلبات، وتعديل الرسائل وحذفها، وتغيير كلمة مرور المدير عبر أداة CLI. يحفظ وقت العملية وهوية المدير إن كانت معروفة، ونوع الإجراء والهدف والنتيجة وعنوان IP ومعرّف الطلب؛ ولعملية CLI تكون قيمة حالة HTTP هي `0` لأنها لا تأتي عبر طلب ويب. في العمليات الجماعية يحفظ المعرّفات المطلوبة (حتى 1000) والعدد المتأثر، دون نصوص الرسائل أو كلمات المرور أو رموز الجلسات؛ يُحفظ بريد محاولة الدخول على شكل تجزئة بدل النص الصريح. تبدأ السجلات من تفعيل هذه النسخة ولا تعيد بناء أحداث سابقة. يُحدّد كل مسار إدارة نوع حدثه صراحةً، ويُؤخذ معرّف الهدف من نتيجة قاعدة البيانات بعد التحقق من المدخلات. تُحفظ التغييرات الناجحة وسجل التدقيق في معاملة واحدة تشمل المنتجات والرسائل وحالات الطلبات وإنشاء جلسة الدخول وإبطالها؛ إذا فشل السجل تتراجع العملية. تُسجَّل المحاولات المرفوضة أو الفاشلة بصورة «أفضل جهد» بعد الاستجابة، ولا يمكن ضمان تسجيلها عند تعطل مخزن السجل. تغيير كلمة المرور عبر CLI مسجّل ضمن معاملته أيضًا. للنشر الحساس يلزم إرسال نسخة إلى مخزن سجلات مستقل محمي من التعديل، وتحديد سياسة احتفاظ ومراقبة مناسبة.

تنتهي جلسة المدير بعد 20 دقيقة من الخمول يفرضها الخادم، أو بعد 8 ساعات من إنشائها أيهما أسبق. لا تُعيد زيارة اللوحة بعد انتهاء المهلة إحياء الجلسة القديمة.

حماية دخول الإدارة تُخزّن عدادات المحاولات في PostgreSQL لتبقى بعد إعادة تشغيل Node وتُشارك بين نسخه. يُسمح بحد أقصى 10 محاولات لكل عنوان IP في 15 دقيقة، ومع 5 محاولات للبريد المستهدف يبدأ تأخير تدريجي (2 ثم 4 ثوانٍ، حتى 60 ثانية). يُعاد ضبط عداد الحساب والعنوان بعد تسجيل دخول ناجح، وتُحذف العدادات المنتهية دوريًا. تعيد الاستجابة `429` و`Retry-After` برسالة عامة عند بلوغ الحد، دون بيان ما إذا كان الحساب موجودًا. قد يستطيع مهاجم مواصلة تعطيل الدخول مؤقتًا بتكرار المحاولات؛ يُنصح بإضافة MFA ومراقبة تنبيهات الدخول للإنتاج.

في التطوير والإنتاج افصل حساب ترحيل قاعدة البيانات عن حساب تشغيل الويب. شغّل `npm --prefix server run db:prepare` مرة واحدة قبل تشغيل الموقع باستخدام `MIGRATION_DATABASE_URL` في بيئة الأمر فقط، وبحساب يملك الجداول؛ ينشئ الجداول وحساب المدير ولا يضيف منتجات تجريبية. أنشئ حساب PostgreSQL جديدًا مثل `mctc_app` بصلاحيات `LOGIN` فقط، دون `SUPERUSER` أو `CREATEDB` أو `CREATEROLE` ودون ملكية قاعدة البيانات أو الجداول. امنحه الصلاحيات المحددة في `deploy/postgres-runtime-grants.sql` بعد الترحيل، مثلًا باستخدام `psql` مع `-v runtime_role=mctc_app`. أعد تطبيق المنح بعد أي ترحيل يضيف جداول أو تسلسلات جديدة. لا تستخدم حساب `postgres` في `DATABASE_URL` الخاص بخادم الويب؛ اجعله يشير إلى الحساب المحدود. لا تحفظ `MIGRATION_DATABASE_URL` في `server/.env`، واحذفه من بيئة عملية الويب قبل التشغيل.

مثال داخل `psql` المتصل بحساب مالك قاعدة البيانات، بعد `db:prepare`:

```sql
create role mctc_app login nosuperuser nocreatedb nocreaterole noreplication;
\password mctc_app
```

ثم من جذر المشروع، مع توفير `MIGRATION_DATABASE_URL` مؤقتًا من مدير الأسرار أو جلسة النشر دون طباعته في سجل الأوامر:

```bash
psql "$MIGRATION_DATABASE_URL" -v ON_ERROR_STOP=1 -v runtime_role=mctc_app -f deploy/postgres-runtime-grants.sql
unset MIGRATION_DATABASE_URL
```

اضبط `DATABASE_URL` في `server/.env` لحساب `mctc_app` فقط. لا تجعل خادم الويب يرث متغير `MIGRATION_DATABASE_URL`؛ يرفض التشغيل إن وُجد. نموذج المنح يفترض قاعدة بيانات مخصصة للمشروع ويزيل صلاحية `CREATE` العامة من مخطط `public` داخل تلك القاعدة.

بعد تجهيز قاعدة البيانات شغّل `npm --prefix server run check:production` و`npm run build` ثم `npm start` من جذر المشروع. يفرض أمر `npm start` وضع الإنتاج، ويتحقق الخادم من HTTPS في عنوان الإدارة وعناوين الواجهة، ومن أن `BIND_HOST` محلي أو عنوان خاص محدد، ومن أن حساب قاعدة البيانات ليس مالكًا للجداول أو قادرًا على إنشاء كائنات داخل `public`. يفحص أمر `check:production` كذلك أن منفذَي Vite المحليين `5173` و`5174` غير مشغّلين. لا يجري ترحيل الجداول أو إنشاء المدير عند بدء خادم الإنتاج؛ نفذ `db:prepare` بعد كل تحديث يتطلب ترحيلًا. يقدّم Express الموقع العام عند وصول الطلب باسم `mctc.ly`، ولوحة الإدارة المحمية عند وصوله باسم `admin.mctc.ly`. اضبط `ADMIN_HOST=admin.mctc.ly` و`ADMIN_URL=https://admin.mctc.ly` و`CLIENT_URL` على عناوين HTTPS الحقيقية فقط، دون عناوين التطوير المحلية. قيمة `ADMIN_URL` في `server/.env.example` مخصصة للتطوير ويجب تغييرها قبل النشر. لا تنشر `admin/dist` على خادم ملفات عام أو CDN؛ يجب أن تمر طلبات النطاق الفرعي كلها عبر Express حتى تبقى ملفات اللوحة محمية.

تُرسل ترويسات CORS الآن للمسارات العامة المطلوبة فقط (المنتجات المنشورة، إرسال الطلبات ورسائل التواصل، وفحص الصحة)، ولعناوين الواجهة العامة المسموحة. لا تُرسل لمسارات تسجيل الدخول والجلسة وقاعدة البيانات وإدارة الطلبات والرسائل وتعديل المنتجات، ولا لأي طلب يحمل جلسة مدير. يمكن تحديد العناوين العامة صراحةً عبر `PUBLIC_CORS_ORIGINS`؛ إن تُرك فارغًا، تُستخدم عناوين `CLIENT_URL` بعد استبعاد نطاق الإدارة ومنفذ التطوير `5174`. لا تعتمد على CORS وحده كحماية للإدارة؛ الجلسة وCSRF والتحقق من الصلاحيات تبقى مطلوبة.

يستمع Node افتراضيًا على `127.0.0.1:5000` فقط (`BIND_HOST` و`PORT` في البيئة)، ويثق بعنوان الوكيل المحلي بدل الثقة بعدد قفزات. نموذج Nginx يستبدل `X-Forwarded-For` بعنوان الاتصال الفعلي ولا يمرر قيمة يضعها العميل. اترك المنفذ `5000` مغلقًا من الشبكة العامة في الجدار الناري؛ لم تُفحَص قواعد الجدار الناري الفعلية ضمن المشروع. إذا كان الوكيل على خادم آخر أو داخل حاوية، اضبط `BIND_HOST` وفق الشبكة الخاصة وأضف عنوان IP المحدد للوكيل إلى `TRUSTED_PROXY_IPS`، مع تقييد الوصول إلى المنفذ في الجدار الناري. إذا كان الموقع وراء CDN، اضبط `real_ip` في Nginx لعناوين CDN الموثوقة فقط قبل الاعتماد على حدود المعدل لكل زائر.

للتحقق على خادم الإنتاج نفسه: نفّذ `nginx -t`، ثم تحقق باستخدام `curl -I http://mctc.ly/` من التحويل إلى HTTPS، و`curl -I https://mctc.ly/` و`curl -I https://admin.mctc.ly/login` من صلاحية TLS واستجابة النطاقين. راجع `ss -lntp` لتتأكد أن 80 و443 فقط مكشوفان للعامة، وأن 5000 مربوط بعنوان داخلي، و5432 مربوط بعنوان محلي أو شبكة قاعدة بيانات خاصة، وأن 5173 و5174 (خادما Vite) غير مشغّلين في الإنتاج. افحص قواعد الجدار الناري ومجموعة أمان السحابة من جهاز خارج الخادم للتأكد من رفض الاتصال المباشر بالمنفذين 5000 و5432. فحص `check:production` لا يثبت حالة الجدار الناري أو الشهادة الفعلية، وإنما يفحص إعداد التطبيق وحساب PostgreSQL فقط.

تتطلب صفحة دخول الإدارة وعمليتا إضافة المنتج وتعديله Cloudflare Turnstile. عند تشغيل الخادم بـ`NODE_ENV=development` وغياب مفتاحَي الإدارة، تظهر تلقائيًا أداة Cloudflare المرئية بمفاتيح الاختبار الرسمية، مثل الصورة التي تحمل عبارة «For testing only». هذا اختبار محلي فقط، ولا يوفر حماية حقيقية. إذا أضفت مفتاحًا واحدًا دون الآخر، لا تُستخدم المفاتيح التجريبية ويظهر خطأ إعداد واضح.

في الإنتاج أنشئ Widget مستقلًا للإدارة في Cloudflare، واسمح له بـ`admin.mctc.ly` فقط. ضع مفتاح الموقع في `ADMIN_TURNSTILE_SITE_KEY` والمفتاح السري في `ADMIN_TURNSTILE_SECRET_KEY` داخل `server/.env`؛ لا تضع المفتاح السري في الواجهة. مفاتيح الاختبار مرفوضة عند `NODE_ENV=production`. إذا أردت اختبار مفاتيح حقيقية محليًا فاستخدم Widget آخر بنطاقات `localhost` أو `127.0.0.1` أو `admin.localhost`؛ لا تُضف النطاقات المحلية إلى Widget الإنتاج. يتحقق الخادم من الرمز ونوع العملية واسم النطاق قبل فحص بيانات الدخول أو استقبال ملفات المنتج عند استخدام المفاتيح الحقيقية. افتراضيًا يقبل الخادم في الإنتاج اسم `ADMIN_HOST` فقط، وفي التطوير الأسماء المحلية المذكورة؛ يمكن تخصيص ذلك بـ`ADMIN_TURNSTILE_HOSTNAMES`. مفاتيح Turnstile العامة للزبائن تبقى منفصلة.

الأيقونات SVG محلية، وخط Alexandria يُضمَّن في ملفات البناء؛ السكربت الخارجي الوحيد الذي تحتاجه لوحة الإدارة هو Cloudflare Turnstile. تسمح سياسة CSP للوحة بسكربت وإطار Turnstile من `https://challenges.cloudflare.com` وباتصاله للتحقق، دون `unsafe-inline` أو `unsafe-eval` في الإنتاج. صفحة الدخول تستخدم ملفات CSS وJavaScript محلية بجانب سكربت Turnstile. سياسة Vite أثناء التطوير أوسع قليلًا للسماح بالتحديث الفوري (HMR)؛ سياسة الإنتاج هي المرجع الأمني.

يوجد نموذج Nginx جاهز في `deploy/nginx.mctc.conf.example`. أنشئ سجل DNS من نوع `A` أو `CNAME` لـ`admin.mctc.ly`، وثبّت شهادة HTTPS تشمل النطاق الفرعي، ثم فعّل إعداد Nginx. الروابط القديمة التي تبدأ بـ`/admin` تُحوّل في التطوير إلى `http://127.0.0.1:5174`، وفي الإنتاج إلى `https://admin.mctc.ly`.

## حساب التشغيل المحلي وتسجيل الخروج

أصبح الاتصال المحلي الحالي يستخدم `mctc_runtime`؛ لا يملك إنشاء الجداول، أو تعديل حسابات المديرين، أو تعديل سجل التدقيق وحذفه. يحتفظ `server/.env` باتصال التشغيل فقط. ملف `server/.env.migrations` مستبعد من Git، وتقرؤه أداتا `db:prepare` و`admin:password` فقط؛ لا يستورده خادم الويب. هذا الملف إعداد محلي، ولا تنسخه إلى خادم تشغيل الإنتاج؛ وفّر اتصال الترحيل من بيئة مهمة النشر المنفصلة.

لتحويل قاعدة محلية موجودة ومجهزة مسبقًا من اتصال إداري إلى حساب جديد محدود: شغّل `node server/scripts/provision-runtime.mjs` من جذر المشروع مرة واحدة. يولّد كلمة مرور عشوائية دون طباعتها، وينشئ الحساب ويطبّق المنح ويحدّث ملف الاتصال. يرفض الكتابة فوق بيانات ترحيل موجودة أو إنشاء حساب بالاسم نفسه. أعد تشغيل API بعد تغيير الاتصال. لا تستخدم اتصال `postgres` الوارد في مثال الإعداد الأولي لتشغيل الويب؛ يرفضه الخادم حتى أثناء التطوير.

لا تنتقل واجهة الإدارة إلى صفحة الدخول إلا بعد تأكيد الخادم نجاح الخروج. عند فشل الشبكة أو الخادم أو التحقق الأمني، تبقى الصفحة وتظهر رسالة وزر لإعادة المحاولة. حذف الجلسة وسجل الخروج داخل معاملة واحدة؛ تُمسح Cookie بعد نجاحها.

## API المختصر

- `GET /api/auth/turnstile-config` مفتاح موقع Turnstile العام الخاص بالإدارة فقط.
- `POST /api/auth/login` تسجيل الدخول وإنشاء الجلسة، ويتطلب `turnstileToken`.
- `GET /api/auth/session` التحقق من الجلسة والحصول على رمز CSRF.
- `POST /api/auth/logout` إبطال الجلسة.
- `GET /api/products` عرض المنتجات.
- `GET /api/products/:id` تفاصيل منتج.
- `GET /api/products/cart/items?ids=1,2` بيانات مختصرة للمنتجات المتاحة داخل السلة.
- `POST /api/orders` حفظ طلب عرض سعر والتحقق من المنتجات والكميات وCloudflare Turnstile، ثم إعادة رابط WhatsApp جاهز. لا يعني فتح WhatsApp أن العميل أرسل الرسالة؛ تُحفظ الحالة `pending_whatsapp` حتى يؤكدها فريق العمل.
- `GET /api/orders?status=confirmed` يدعم فلترة الطلبات حسب `pending_whatsapp` أو `confirmed` أو `archived` (أو `all`)، مع البحث والترقيم قبل إرسال النتائج.
- `PATCH /api/orders/:id/status` تغيير حالة الطلب إلى `pending_whatsapp` أو `confirmed` أو `archived`، ويتطلب جلسة مدير ورمز CSRF.
- `POST /api/products` إضافة منتج، يحتاج جلسة مدير ورمز CSRF وترويسة `X-Turnstile-Token`، ويقبل `imageFiles` لعدة صور مرفوعة، و `images` لروابط الصور، و `datasheetUrls` لعدة روابط داتا شيت، و `datasheetFile` لملف PDF.
- `PUT /api/products/:id` تعديل منتج، يحتاج جلسة مدير ورمز CSRF وترويسة `X-Turnstile-Token`، ويقبل الحقول والملفات نفسها بالإضافة إلى `revision` المقروء من تفاصيل المنتج. إذا حفظ تبويب آخر نسخة أحدث يُعاد `409` ولا تُستبدل بياناته أو ملفاته.
- `DELETE /api/products/:id` حذف منتج، يحتاج جلسة مدير ورمز CSRF.

الملفات المرفوعة تُقبل فقط بصيغ JPG/PNG/WebP للصور وPDF للداتا شيت بعد مطابقة الامتداد مع توقيع المحتوى، وتُحفظ بأسماء يولدها الخادم داخل `server/uploads`. يفك الخادم ترميز كل صورة جديدة ويعيد ترميزها بصيغة WebP، مع حد 40 مليون بكسل؛ ولا تُحفظ بياناتها الأصلية أو أي محتوى زائد ملحق بها. مسار `/uploads` متاح على نطاق الموقع العام فقط، وممنوع على نطاق الإدارة في Express وNginx النموذجي وخادم Vite الخاص باللوحة أثناء التطوير. لا يقدّم المسار إلا الامتدادات المسموحة، مع `nosniff` وسياسة عزل؛ وتُرسل ملفات PDF بصفة تنزيل (`attachment`) لا كصفحات داخل الموقع. تبقى الصور القديمة بالامتدادات المسموحة قابلة للعرض دون إعادة ترميز تلقائية، أما الملفات القديمة بامتدادات أخرى فيُمنع الوصول إليها عبر هذا المسار. ملفات PDF لا تُنشر إلا بعد فحص بنيتها بواسطة qpdf ورفض المحتوى التفاعلي المحظور وفحصها بواسطة ClamAV بتعريفات حديثة. تُحجب الملفات القديمة أيضًا حتى اعتماد بصمتها بعد الفحص. عند تعطل الفحص يُرفض الرفع بدل تجاوزه. راجع [إعداد وتشغيل فحص PDF](server/PDF-SECURITY.md)، وشغّل `npm --prefix server run pdf:scan` لفحص الملفات الموجودة دون حذف أصولها.

يُسمح للمدير بحد أقصى 60 عملية إضافة/تعديل منتج خلال ساعة، ويُضبط الحد الإجمالي لمساحة `server/uploads` بواسطة `UPLOAD_MAX_BYTES` (افتراضيًا 1 GiB)، مع احتساب الملفات المؤقتة. تُحذف الملفات التي ولّدها النظام عند فشل العملية أو عند حذف المنتج أو استبدال ملفاته، بشرط ألا يشير إليها منتج آخر. ينظّف الخادم الملفات المولدة غير المرتبطة بعد مرور 24 ساعة، عند الإقلاع ثم كل ساعة. لا يلمس التنظيف التلقائي الملفات القديمة التي لا تتبع نمط الأسماء الجديدة؛ راجعها يدويًا قبل حذفها. هذه الحصة تخص قرص الخادم الواحد؛ عند تشغيل عدة خوادم بمخازن ملفات منفصلة يلزم مخزن مركزي وحصة مشتركة.

لم يعد مسار API الجذري يعرض رسائل العملاء أو بيانات حسابات الإدارة. كما يتطلب `status=all` في قائمة المنتجات جلسة مدير، ولا تُعرض المنتجات غير المنشورة عبر رابط التفاصيل العام.

أخطاء التحقق المتوقعة تُعاد برمز `400` ورسالة مفهومة، والتعارض برمز `409`، والملفات أو الطلبات الكبيرة برمز `413`. الأعطال الداخلية تُعاد برسالة عامة ورمز `500`، وتعطّل اتصال قاعدة البيانات المؤقت برمز `503`، بينما تبقى التفاصيل التقنية في سجل الخادم فقط. تتضمن استجابات أخطاء الخادم معرّف `errorId` وترويسة `X-Error-ID` للمطابقة مع سجل الخادم؛ لا يظهر نص الاستثناء الداخلي للعميل.

سلة العميل لا تتضمن أسعارًا أو دفعًا إلكترونيًا. يمكن وضع 12 منتجًا مختلفًا كحد أقصى، و99 قطعة من كل منتج. يستخدم الطلب رقم WhatsApp المحدد في `CONTACT_WHATSAPP_NUMBER` ضمن `server/.env`، ونفس مفتاحَي Turnstile المستخدمين في صفحة التواصل. ينشئ أمر `db:prepare` جدولَي `orders` و`order_items` قبل تشغيل API. تظهر الطلبات في لوحة التحكم مع البحث برقم الطلب أو رقم الهاتف أو جزء منه أو اسم المنتج أو رقم الموديل.

يستخدم إرسال الطلب مفتاحًا لمنع التكرار عند إعادة المحاولة بالبيانات نفسها. إذا تغيّرت بيانات العميل أو المنتجات، يُنشأ مفتاح جديد؛ ويرفض API إعادة استخدام مفتاح قديم لبيانات مختلفة برمز `409`. أثناء انتظار الحفظ تُعطَّل تعديلات السلة في الصفحة، ولا تُزال بعد النجاح إلا عناصر الطلب الذي أُرسل فعلًا. يقبل التحقق من الهاتف الأرقام العربية والهندية ويحوّلها إلى أرقام لاتينية، ويتطلب 6 إلى 20 رقمًا فعليًا. في صفحة التواصل يلزم أن تتكون الرسالة من 15 إلى 2500 حرف، ويظهر عداد أثناء الكتابة.

## استعادة الطلب وتصحيح صفحات المنتجات

تظهر بعد حفظ طلب السلة رسالة تأكيد مستقلة برقم الطلب وزر «فتح WhatsApp»، حتى إذا حُجبت نافذة WhatsApp أو أغلقها العميل أثناء الحفظ. يُحفظ آخر رابط مؤكد ومفتاح الطلب المعلّق وبصمة بياناته في `sessionStorage` لمدة تصل إلى 24 ساعة ضمن جلسة التبويب؛ يستمران بعد تحديث الصفحة، وينتهيان بإغلاق جلسة التبويب أو انتهاء المدة. البصمة SHA-256 لا تخزّن حقول العميل نصًا، لكن رابط WhatsApp المؤكد يحتوي على نص الرسالة. لا يُحفظ رمز Turnstile. يُعاد استخدام المفتاح لنفس البيانات واللغة إذا لم تتأكد النتيجة، ويتغير عند تغيير الطلب أو تأكيد نجاحه. إذا تعذر التخزين قبل الإرسال تظهر رسالة ولا يُرسل طلب غير قابل للاستعادة. يبقى قيد `request_key` الفريد في PostgreSQL ومسار إعادة الطلب السابق فعالين.

تُصحح قائمة المنتجات رقم الصفحة القديم إلى آخر صفحة متاحة، أو الصفحة الأولى عند خلو النتائج، وتستبدل الرابط مع الاحتفاظ بالبحث والفلاتر وتجلب الصفحة الصحيحة مجددًا. لا تظهر رسالة «لا توجد نتائج» أثناء التصحيح.
